01

FROM EVIDENCE TO RESULTS

一份报告，如何形成

  1. 01 / DEFINE明确比较对象

    对齐需求和版本；有冻结契约时，两端使用同一份功能清单。

  2. 02 / OBSERVE采集双端证据

    读取测试证据、页面与截图，以及每端独立记录的耗时和 Token。

  3. 03 / CALCULATE计算有效维度

    换算到百分制，排除缺失或降级项，再按有效权重计算。

  4. 04 / EXPLAIN呈现与追溯

    展示两端分数、维度差异、原始数据，以及未计分的原因。

示意图说明数据的评估路径。历史记录的采集完整度可能不同，实际以报告中的证据和降级标记为准。

03

WHAT IS ACTUALLY VERIFIED

如何判断功能与 UI

FUNCTION / 40%

逐条功能，逐条看证据

功能矩阵把需求拆为可核对的条目。已覆盖计 1，部分覆盖计 0.5，未覆盖计 0，再除以功能点总数。

功能分 =（✓ 数量 + 0.5 × ◐ 数量）÷ 功能总数 × 100

例如 10 个功能点，8 个覆盖、1 个部分覆盖、1 个未覆盖，功能分为 85。

A运行证据Hypium、JUnit 或独立设备交互记录，需核对具体断言与运行结果。
B源码覆盖证据冻结契约的 slug 或测试名称在测试源码中命中，只说明有对应测试代码。
C历史兜底缺少逐条矩阵的早期报告可能按构建状态计算，信息量较低。

“有测试代码”和“测试运行通过”是不同证据。功能矩阵的备注会说明来源；即使覆盖率为 100%，也不能据此宣称所有真实交互都通过。

VISUAL REVIEW / 20%

以双端截图进行视觉评审

自动评审按以下五项分别打 1–5 分，再加权。当前服务通常每端采样 3 次，取平均后映射到百分制；具体样本数、模型和原始采样值保存在报告中。

维度判断内容权重

布局合理性层级、对齐、留白与空间分配25%

UI 分 =（五分制平均分 − 1）÷ 4 × 100

4.5 分 → 87.5 分；五分制相差 0.5 档 → 百分制相差 12.5 分。

截图评审反映可见界面表现，不验证按钮实际行为、完整可访问性或业务正确性。历史人工评分与自动评审应通过报告来源区分；单侧缺图时不做完整双端 UI 比较。

PAGES / 20%

页面数量如何进入分数

页面结构提取器从鸿蒙 main_pages 页面清单、安卓 Manifest 的 Activity 及源码跳转信息推导页面与路由，同时记录节点、边等结构信息。综合分的这一项目前只使用页面计数：该端页数 ÷ 双端最多页数 × 100。例如 2 页与 3 页，页面分分别为 66.67 和 100。

页面更多会在当前数量公式中得分更高，但不代表体验更好，也不代表需求完成得更好。单 Activity 下的声明式页面也可能超出静态提取器的识别范围。结构是否合理仍需结合需求、截图和路由证据阅读。

04

TIME & TOKEN ACCOUNTING

效率既看时间，也看用量

生成耗时

读取每端任务记录的 duration_ms，页面以秒或分秒展示。当前 Claude Code 执行器在启动生成进程前、会话退出后独立计时，包含会话内的工具与构建时间。

它不是两个并行任务耗时之和，也不等于用户从提交到看到报告的等待时间；队列、上传、后续截图与评审可能发生在该区间之外。

时长分 = 双端较短耗时 ÷ 该端耗时 × 100

双端为 300 秒与 450 秒时，分别得到 100 与 66.67 分。

Token 消耗

当前执行器读取模型会话返回的 usage.input_tokens + usage.output_tokens。它衡量本记录采集的输入与输出用量，不直接等于费用。

该字段未单独加总 cache_read 或 cache_creation 等缓存计费项。不同采集器和历史人工交付可能没有完整用量，不把未采集记作“零消耗”。

Token 分 = 双端较少 Token ÷ 该端 Token × 100

双端为 60,000 与 80,000 Token 时，分别得到 100 与 75 分。

效率分 = 有效的时长分与 Token 分的平均值

每个子项都要求双端数值为正且未降级。一项无效时只用另一项；两项都无效时，整个效率维度退出综合分。

06

READ THE SCORE WITH CONTEXT

高分、胜负与“通过”，分别代表什么

综合分是比较指标

卡片中较高的分数表示有效维度的加权结果更高，不保证每一项都占优。当前示例里，鸿蒙 UI 得分更高，安卓因为时间和 Token 更省，综合分仍更高。

UI 胜负使用独立差值

自动视觉评审中，鸿蒙分 − 安卓分 ≥12.5 为“鸿蒙胜”，≤−12.5 为“安卓胜”，其余为“基本持平”。该阈值不会再次扣除或奖励综合分。

报告达标是另一套规则

历史报告的 pass／fail／degraded 标签由其保存的阈值快照与逐维判据生成，并不等于“综合分超过某条及格线”。降级项不作为失败项，但报告会保留降级标记。

旧版默认判据保存为功能 diff≤0、UI 差≥12.5、时长差<0、Token 差<0。历史功能差值的符号与“覆盖越多越好”的直观方向可能不同，因此请同时核对原始两端数值、formula、threshold_snapshot 和逐条证据，不从 pass 标签反推实际功能优劣。

阅读顺序先看构建状态→核对功能与 UI 证据→查看缺失维度→再比较综合分与效率
